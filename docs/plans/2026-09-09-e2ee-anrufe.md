# E2EE-Anrufe — Planung (2026-09-09)

> Ziel: Anrufe (Audio + Video, 1:1 und private Gruppen) Ende-zu-Ende
> verschlüsselt — der Server (LiveKit-SFU) sieht nur noch Chiffrat, wie bei
> WhatsApp. Heute: transportverschlüsselt (DTLS-SRTP), der SFU könnte
> mitlesen (dokumentierte Grenze in `docs/UEBERGABE-MOBILE.md`, Anrufe-Epic).

## Bausteine — alles vorhanden, nichts Neues nötig

1. **LiveKit eingebautes E2EE** (`livekit-client` 2.18.9, **Apache-2.0**, im
   Repo installiert — keine neue Abhängigkeit, Lizenz passt):
   `ExternalE2EEKeyProvider` + `livekit-client/e2ee.worker`, Room-Option
   `encryption: { keyProvider, worker }` (das Feld `e2ee` ist deprecated),
   `setKey(...)` **vor** `room.connect()`. Verschlüsselt Audio-, Video-Tracks
   und Datenkanäle; der SFU leitet nur Chiffrat. `room.isE2EEEnabled` als
   Anzeigebasis.
2. **Schlüsselübergabe ohne neuen Serverweg:** die bestehenden
   verschlüsselten Postfach-Umschläge. Neuer Frame-Typ
   `anrufSchluessel: { anrufId: string; schluessel: string }` (32
   Zufallsbytes, base64) in `nachrichtNutzlast.ts`, daneben
   Builder + Parser wie bei `reaktion`/`bearbeitung` (fail-closed).
   Verteilung: DM → `versendeFrame`-Weg (alle Geräte der Gegenstelle +
   eigene), Gruppe → Megolm-Gruppenweg (`gruppe/frameSenden.ts`). Der Server
   bleibt blindes Postfach — keine Route, keine Migration.

## Ablauf

**Initiator** (bei E2EE-fähigem Ziel — verschlüsselte DM bzw. private
Gruppe): 32 Zufallsbytes generieren → Schlüssel-Umschlag verschicken
(`sendeAnrufSchluessel` / Gruppenvariante) → WS-Klingeln wie heute → Room
mit `encryption`-Option, `setKey` vor `connect`.

**Empfänger:** Klingeln → Annahme: auf den Schlüssel warten
(Postfach-Abholung anstoßen, Timeout ~10 s, Overlay zeigt „Schlüssel wird
übertragen…") → E2EE-connect. **Fail-closed:** Schlüssel trotz Timeout
nicht da → Anruf bricht ab mit klarer Meldung, KEINE stille Rückfalloption
auf unverschlüsselt. Bei Klartext-DMs (kein E2EE-Weg): Verhalten wie heute,
Overlay zeigt ehrlich „nur Transportverschlüsselung".

**Overlay:** Dauer-Badge — „Ende-zu-Ende verschlüsselt" (E2EE aktiv,
`isE2EEEnabled`) / „nur Transportverschlüsselung" (Klartext-Weg).

## Verifizierung

- Unit (`web/test/anruf-schluessel.test.ts`, Node-Testläufer): Frame-Builder/
  -Parser round-trip + fail-closed bei kaputten Nutzlasten; Warte-Logik
  (injizierbare Uhr/Abruf) — Schlüssel trifft ein → verbindet, Timeout → Abbruch.
- Live: Videoanruf Emulator (alice) ↔ Browser (bob): beidseitig
  `isE2EEEnabled === true`, Ton + Bild laufen; Negativ-Test: absichtlich
  falscher Schlüssel → Medien kommen nicht an (Beweis, dass wirklich
  verschlüsselt wird).

## Bewusste Grenzen (Ceilings, mit Upgrade-Pfad)

- **Ein gemeinsamer Schlüssel je Anruf** statt pro Teilnehmer geratchet
  (MLS-artig). Bei 1:1 und kleinen Gruppen der übliche Kompromiss; Upgrade:
  Custom KeyProvider mit Keyring.
- **Metadaten bleiben beim Server:** wer wen ruft, wann, wie lange — kennt
  der Server weiter (auch WhatsApp kennt das). Nur die Inhalte (Ton, Bild,
  Datenkanäle) werden blind.
- **Kein „später beitreten" ohne Schlüssel:** der Schlüssel-Umschlag liegt
  dauerhaft im Postfach des Geräts, ein späterer Beitritt holt ihn — Gerät
  ohne Postfach-Zugang (frisch gekoppelt, Abholung nicht gelaufen) kann
  nicht beitreten (fail-closed, s. o.).
- **Kein SRTP-/Geräte-Verifizierungs-QR** („ist das wirklich Bob?") —
  Sicherheitsnummer-Vergleich wie in WhatsApp wäre ein eigener Baustein.
