Hosting Pulse yourself

Pulse runs as one Docker container. The web app and user identity stay with the Cloud — your people sign in at howispulse.com and connect from there. Your server only needs outbound HTTPS.

Before you start

  • An approved instance. In the app: create an account, enable MFA, apply under Settings → Your own server, wait for approval.
  • A server with Docker and Docker Compose.
  • A DNS A record pointing at the server IP, for example chat.example.com. Set it before the first start, otherwise the certificate never arrives.
  • The ports below open.
PortProtocolWhat for
80, 443TCPHTTP/HTTPS — the app and the Let’s Encrypt challenge
3478TCP + UDPcoturn — NAT traversal for voice
7882–7892UDPLiveKit WebRTC — voice and HQ stream ICE
1936TCPHQ streaming ingest (RTMPS)
8189UDPHQ stream playback (WHEP)
 
ufw allow 80,443/tcp
ufw allow 3478
ufw allow 7882:7892/udp
ufw allow 1936/tcp
ufw allow 8189/udp
Only 80 and 443 are needed for chat and sign-in. Everything else is voice and streaming — leave those ports closed and you get a server where chat works and calls do not.

The fast way: installer script

One command, and the server keeps itself up to date afterwards. Generate it under Settings → Your own server → Set up server.

curl -fsSL https://howispulse.com/install | PULSE_BOOTSTRAP_TOKEN=<YOUR_TOKEN> bash

Everything below is the manual route — for your own proxy or your own update strategy.

Manual installation

There are two ways, and one question decides between them: is anything already listening on ports 80 and 443 on this machine?

ss -tlnp | grep -E ':(80|443)\s'

Open the matching panel below. Each one is complete — every command you need, in order. You never have to read the other.

Pick the wrong one and the container will not start — and it can take the other sites on the machine down with it.
Nothing is listening — standalone docker-compose.yml

The machine belongs to Pulse alone. The embedded Caddy fetches its own Let’s Encrypt certificate, so 80 and 443 must be reachable from outside.

5 steps
01

Download the .env

Settings → Your own server → Set up server → Manual installation → Download .env. The file is filled in completely. You enter nothing by hand.

One download only. Each one generates a new secret and invalidates the previous. Keep the file safe — it is also your registry password in step 3.

Check two values before you go on:

grep -E "^PULSE_(HOSTNAME|INSTANCE_OWNER_ID)=" .env
ValueWhy it matters
PULSE_INSTANCE_OWNER_ID The account that applied for the instance. Only that account becomes admin. There is no safety net — getting it wrong means a database edit later. If it is not the account you want, apply again now.
PULSE_HOSTNAME Must be exactly the name the server will be reachable under. The sign-in ticket is bound to it.
02

Get the files

mkdir pulse && cd pulse
curl -fsSLO https://howispulse.com/self-host/docker-compose.yml

mv ~/Downloads/pulse-instance-*.env .env

The filename .env is mandatory — Compose looks for exactly that, in the same directory.

03

Sign in to the registry

The image sits in a closed registry. Skip this and the start fails with pull access denied. The credentials are already in your .env:

grep -oP '^PULSE_CLOUD_CLIENT_SECRET=\K.*' .env \
  | docker login registry.howispulse.com \
      -u "$(grep -oP '^PULSE_CLOUD_CLIENT_ID=\K.*' .env)" --password-stdin

Expect Login Succeeded. The pipe matters: --password-stdin keeps the secret out of the process list and your shell history.

04

Start it

docker compose up -d

The first start takes 60–120 seconds: database, migrations, and fetching the certificate. Wait for (healthy):

docker ps --filter name=pulse --format '{{.Names}}\t{{.Status}}'

Some log lines on a first start look like errors and are not — the list is under normal start-up messages.

05

Verify and sign in

curl https://chat.example.com/health                        # {"status":"ok"}
curl https://chat.example.com/.well-known/pulse-server-info

The second one carries the most information. It must show your instance_id and, in capabilities, the entry server-ticket.

No server-ticket means the server predates 28 August 2026 and will accept nobody. An update alone is not enough — it has to be set up again.

Then: howispulse.com → Add server → your hostname. Sign in with the account that applied (step 1) — only that one becomes admin.

Finally run Settings → Your own server → My Instances → Check connection. That is the view from outside, and it catches what a server cannot see about itself.

Opening your server domain directly in a browser shows a blank page. That is intended — a self-host has no login page of its own.
A proxy is running — behind your own proxy docker-compose.behind-proxy.yml

nginx, Traefik, Caddy or Nginx Proxy Manager already holds 80/443. Pulse leaves them alone and serves HTTP on 8080; TLS stays with your proxy.

6 steps
Two things differ from the standalone path. Every docker compose command carries -f docker-compose.behind-proxy.yml, updates included — or set COMPOSE_FILE=docker-compose.behind-proxy.yml in your shell and drop the flag. And there is one extra step at the end: the proxy rule.

05

Add the proxy rule

One rule — the container routes the rest.

WebSocket upgrade must pass through. In Nginx Proxy Manager that is the “WebSocket Support” tick; in nginx it is the Upgrade headers. Without it, sign-in works and chat stays empty — the single most common mistake here.

If your proxy runs on the host

chat.example.com {
    reverse_proxy 127.0.0.1:8080
}

If your proxy runs in a container

Then it cannot reach the host’s 127.0.0.1 — that is its own loopback. Share a Docker network and address Pulse by container name:

docker network create pulse-net
docker network connect pulse-net <your-proxy-container>

Add two blocks to the Compose file. Under the pulse service, indented like ports::

    networks:
      - pulse-net

And at the end of the file, next to volumes::

networks:
  pulse-net:
    external: true

The two blocks share a name and mean different things: the indented one says this service joins that network, the left-aligned one says here is how the network is defined. Then point the rule at the container name:

chat.example.com {
    reverse_proxy pulse:8080
}

Check the YAML without starting anything, then restart:

docker compose -f docker-compose.behind-proxy.yml config >/dev/null && echo "YAML ok"
docker compose -f docker-compose.behind-proxy.yml up -d
Voice and HQ streaming bypass the proxy over UDP. Those ports must stay open either way.

Running it

Updates

Installed with the script? Updates already run on their own. The installer put a timer on the host that pulls a new image and restarts the container. Nothing for you to do — skip to Backups.

Installed manually? Then you update yourself:

# standalone:
docker compose pull && docker compose up -d

# behind your own proxy:
docker compose -f docker-compose.behind-proxy.yml pull && \
  docker compose -f docker-compose.behind-proxy.yml up -d

Put that in a cron job or systemd timer. It is not optional in the long run: a server left on an old version eventually stops matching the Cloud, and then it accepts nobody.

Backups

The container writes periodic pg_dump snapshots to /data/backups/ — daily, seven kept. Tune with PULSE_BACKUP_INTERVAL_SECONDS, PULSE_BACKUP_RETENTION and PULSE_BACKUP_DISABLED. Encryption is the host’s job: put the whole /data volume on an encrypted device (LUKS, ZFS).

docker compose exec pulse pg_dump -h 127.0.0.1 -U pulse dcc > backup-$(date +%Y%m%d).sql

The database is called dcc, the role pulse. -h 127.0.0.1 is required — the Unix socket is not at the default path.

When something is wrong

Two tools. From inside the server:

docker exec pulse pulse-doctor

From outside: Settings → Your own server → My Instances → Check connection. Green inside and red outside means DNS, firewall or proxy — not the server.

Normal start-up messages

All of these appear on a first start and are not errors.

STUN CHANGE_REQUESTcoturn with a single IP address. Enough for NAT traversal.

docker logs pulse 2>&1 | grep -iE "error|fatal|traceback" | tail -20

Media ports cannot be remapped

-p 9882:7882/udp will not work — WebRTC announces its own port number, and a Docker remap does not change what the server says. Bind Pulse to a second IP instead:

-p <IP>:7882-7892:7882-7892/udp

Not admin on your own server

The server logs both the configured owner and who signed in:

docker logs pulse 2>&1 | grep -iE "instance owner|Cloud account"

Two different numbers means the wrong account. To move the server to another account, change PULSE_INSTANCE_OWNER_ID in the .env and restart. Needs PULSE_LOG_LEVEL=info, which is the default — if neither line appears, the container is running quieter than that.

Certificate never arrives

pulse-doctor compares what your hostname resolves to against what this machine looks like from outside. A mismatch is the usual reason. Either the A record points elsewhere, or the network has split ingress and egress — then forward 80/443 here and run with PULSE_TLS_MODE=behind-proxy.

Uninstalling

Remove the auto-update job first. Otherwise the next run brings the container back with an empty volume. If you are not sure which install you have, run both blocks — the wrong one fails harmlessly.
# root install (systemd):
sudo systemctl disable --now pulse-update.timer
sudo rm /etc/systemd/system/pulse-update.{service,timer}
sudo systemctl daemon-reload

# non-root install (user crontab):
crontab -l | grep -v pulse-update.sh | crontab -
Back up before the next step. The volume holds every message, account and upload on this server, and nothing restores it.
# installer path:
docker rm -f pulse
docker volume rm pulse-data          # deletes ALL data

# compose path (volume carries the project name):
docker compose down -v               # removes pulse_pulse-data too

docker compose down without -v keeps the data for a reinstall.

Afterwards delete the instance in the app under My Instances, which frees the hostname. Members remove the server from their own list by right-clicking it.
