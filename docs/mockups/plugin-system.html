Pulse als Plugin-System

Eine visuelle Erklärung — ohne Code. Was bedeutet es, wenn die App "modular" gebaut wird? Was wäre dann ein "Plugin", wo dockt es an, und wie würde z. B. ein Tamagotchi konkret aussehen?

01 — DIE GRUNDIDEE

Wie es heute ist — und wie es sein könnte

Stell dir Pulse heute vor wie einen zusammengeschweißten Lego-Block: alle Steine sind miteinander verklebt. Willst du einen Stein tauschen oder hinzufügen, muss man die ganze Konstruktion aufbrechen. Mit einem Plugin-System gibt es einen Kern mit definierten "Steckplätzen" — alles andere ist andockbar, austauschbar, deaktivierbar.

02 — DIE SCHNITTSTELLEN

Was sind die "Steckdosen"?

Damit ein Plugin andocken kann, muss der Kern definierte Anschlüsse anbieten — ähnlich wie eine Steckdose: standardisierte Form, klare Spannung, niemand muss die Wand aufstemmen. Pulse hätte fünf Haupt-Anschlüsse:

03 — WAS STECKT DRIN

Anatomie eines Plugins

Jedes Plugin ist im Prinzip ein kleiner Ordner mit einem Steckbrief ("Manifest") und ein paar Dateien. Der Steckbrief sagt dem Kern: "Hallo, ich heiße so, ich brauche diese Anschlüsse, ich liefere das hier."

name"tamagotchi" version"0.1.0" author"michael" needs[UI, DB, EV] scope"per-server" enabledtrue
Manifest
Steckbrief mit Name, Version, gewünschten Anschlüssen. Der Kern liest das beim Start und entscheidet: installieren ja/nein.
UI-Stück
Optional: eine kleine Komponente, die irgendwo erscheint — im Beispiel das Tamagotchi-Widget in der Seitenleiste.
Logik
Was passiert, wenn der User auf "Füttern" klickt. Was passiert, wenn eine Stunde vergeht. Reine Plugin-Sache — berührt den Kern nicht.
Eigene Daten
Hunger-Wert, Glücks-Wert, Name des Haustiers. Das Plugin bekommt seine eigene Schublade, andere Plugins kommen da nicht ran.
Event-Haken
"Reagier, wenn jemand eine Nachricht schickt." — so kann das Tamagotchi z. B. glücklicher werden, wenn der Server aktiv ist.
04 — KONKRETES BEISPIEL

Tamagotchi-Plugin — wie würde es ablaufen?

Vom Doppelklick auf die Plugin-Datei bis zum fertigen Haustier in der Seitenleiste. Niemand muss in den Pulse-Code — das Plugin macht alles selbst, weil die Steckdosen da sind.

1
Plugin aktivieren
User schaltet "Tamagotchi" in den Einstellungen ein — oder Server-Admin macht das für alle.
2
Kern liest Manifest
Pulse sieht: "Aha, das Plugin will UI, DB, EV — alles erlaubt."
3
Widget erscheint
Das Tamagotchi-Symbol taucht in der Seitenleiste auf — ohne Pulse-Neustart, ohne Code-Änderung.
4
Plugin reagiert auf Events
Schreibt jemand eine Nachricht, kriegt das Plugin den Event message.created — Tamagotchi wird etwas glücklicher.
5
Daten bleiben isoliert
Hunger/Glück landen in einer eigenen kleinen Schublade. Wird das Plugin deinstalliert, sind sie sauber weg.

05 — DER WEG DAHIN

Wie kommt man hin? Erst aufräumen, dann fünf Schritte.

Vor den fünf eigentlichen Plugin-Schritten muss heute eine Vorarbeit erledigt werden — sonst bauen wir das Plugin-System auf einer wackeligen Grundlage. Erst danach folgen die Schritte, die Pulse modular machen.

⚠ SCHRITT 0 · NOTFALL-AUFRÄUMEN

Erst entwirren, dann modularisieren

Solange das so ist, landet jedes neue Feature wieder im selben überfüllten Topf — egal wie sauber es konzipiert wurde. Reine Code-Verschiebung in thematische Module, keine Verhaltens-Änderung.

Schritt 5 ist nur nötig, wenn fremde Leute Plugins anbieten sollen. Schritt 0 ist allerdings nicht optional — ohne ihn frisst sich jedes neue Feature wieder durch pubsub.py und ws.py.

06 — INTERN vs. EXTERN

Wenn auch Fremde mitmachen sollen

Ein Plugin zu schreiben ist eine Sache — Plugins von fremden Entwicklern sicher installieren zu lassen, ist eine andere. Dafür gibt es zwei realistische Reifegrade, die man nacheinander bauen würde. Stufe A löst schon das meiste, Stufe B ist nur nötig, wenn ein echtes Ökosystem entstehen soll.

STUFE A Interner Vertrauenskreis — du, ich, vertraute Leute
Plugins werden von dir oder Leuten, denen du vertraust gebaut — und können alles. Kein Sandbox-Aufwand, weil niemand absichtlich etwas Böses einbaut. Sie werden zusammen mit Pulse ausgeliefert (oder einzeln nachinstalliert), aber niemand Fremdes hat Zugriff auf das Innenleben.
  • Reicht für 80 % der Modularität — Tamagotchi, Themes, Mini-Spiele, eigene Bots, Custom-Sounds.
  • Plugin-Updates laufen über die normale Pulse-Veröffentlichung — keine Extra-Infrastruktur.
  • Aufwand: Schritte 1–4 aus der Roadmap. Machbar in überschaubarer Zeit.

07 — TRANSPARENZ & KONFLIKT-WARNUNG

Sehen, was Plugins tun — bevor sie sich streiten

Weil jedes Plugin im Manifest deklariert, was es liest und was es schreibt, kann Pulse die Beziehungen automatisch sichtbar machen — mit Konflikt-Warnung, wo zwei Plugins um dasselbe streiten. Der User sieht vorher, dass es Ärger geben könnte, nicht erst, wenn der Status flackert.

Konflikt erkannt: "User-Status" Auto-Status und Status-Timer schreiben beide auf denselben Wert — ohne Regel kämpfen sie um die Hoheit.
Wer soll deinen Status setzen dürfen, wenn beide gleichzeitig wollen?
Manuell schlägt Automatik Wenn du selbst "Mittagspause" setzt, schweigt Auto-Status, bis dein Timer abläuft.
Automatik hat Vorrang Auto-Status setzt immer den Status. Der Timer wird nur sekundär angezeigt.
Eins deaktivieren Du wählst, welches der beiden Plugins du behalten willst — das andere wird ausgeschaltet.

Der Clou: Diese Übersicht und Konflikt-Erkennung baut man einmal in das Plugin-System ein. Danach funktioniert sie automatisch für jedes neue Plugin, auch für solche, die es heute noch gar nicht gibt — weil die Information immer aus dem Plugin-Manifest kommt, nicht aus dem Pulse-Code.

08 — DIE EHRLICHE GRENZE

Wie zuverlässig findet das System Konflikte?

Nicht alles. Das Manifest-System ist eine starke erste Verteidigungslinie — aber es hat Lücken. Ehrliche Antwort: Es macht Konflikte sichtbar, ist aber kein Garant. Trotzdem ist das schon enorm viel wert. Hier, was es kann und was nicht.

✓ Automatisch erkannt

✓ Zwei Plugins schreiben dieselbe Sache Status, Nachrichten, Channel-Namen — alles, was im Manifest deklariert ist.
✓ Zwei Plugins wollen denselben UI-Platz Sidebar-Knopf, Hotkey, Menü-Eintrag — nur einer kriegt den Slot.
✓ Lese-Schreib-Race Plugin A liest etwas, das Plugin B gleichzeitig verändert.
✓ Berechtigungs-Konflikte Plugin will mehr Rechte, als der User ihm zugestanden hat.

✗ Bleibt unsichtbar

✗ Reihenfolge-Probleme Übersetzer-zuerst vs. Filter-zuerst — beides "richtig", aber unterschiedliches Ergebnis.
✗ Semantische Konflikte A schreibt eine Zahl, B erwartet Text — beide deklarieren brav "Nachricht".
✗ Indirekte Effekte Lautstärke-Plugin verändert Mikrofon-Pegel — Spracherkennung versteht nichts mehr.
✗ Performance-Summe Jedes Plugin allein leicht, zehn zusammen lahm. Keiner hat allein etwas falsch gemacht.
✗ Manifest-Lügen Plugin sagt "lese nur" — tut aber heimlich was anderes.

🛡 Schicht für Schicht — wie man immer mehr fängt

Keine einzelne Methode löst alles. Aber gestapelt schrumpfen die blinden Flecken — was durch das erste Sieb fällt, fängt das zweite. Jede Schicht ist zusätzlicher Aufwand, aber sie deckt eine neue Bug-Klasse ab.

SCHICHT 1
Manifest-Abgleich
Pulse vergleicht alle Manifeste — offensichtliche Kollisionen sind sofort sichtbar (das, was Sektion 7 zeigt).
fängt das meiste
SCHICHT 2
Schema-Prüfung
Plugins müssen das Format angeben (z. B. "Text, max. 50 Zeichen"). Format- und Typ-Konflikte werden erkennbar.
+ Format-Bugs
SCHICHT 3

+ Endlosschleifen
SCHICHT 4
Community-Reports
Bekannte Konflikt-Paare werden gesammelt. Pulse warnt schon bei der Installation: "Diese Kombination macht oft Probleme."
+ Schwarm-Wissen

🪤 Was trotzdem durchrutschen kann

Selbst mit allen Schichten gibt's Konflikte, die erst im Alltag auffallen. Das ist nicht Pulses Schuld — die haben prinzipiell jedes Plugin-System der Welt.

RUTSCHT DURCH Bösartiges Plugin lügt

Manifest sagt "lese nur" — in Wirklichkeit schreibt es heimlich. Dagegen hilft nur echte Sandbox-Technik.

RUTSCHT DURCH Effekt-Ketten

A → B → C, wo niemand allein etwas Verbotenes tut, aber das Endergebnis kaputt ist.

RUTSCHT DURCH Hardware-Eigenheiten

Funktioniert auf 99 PCs perfekt, auf einem zickt's wegen einer komischen Soundkarte oder Treiber-Version.

DAS ECHTE VERSPRECHEN
Das System ist ein Sichtbarmacher, kein Garant. Es ersetzt nicht das Testen — aber es verwandelt rätselhaftes Verhalten in ein konkretes, benennbares Problem.
