Identitäts-Modelle für Pulse

Wie behalten wir die einheitliche Identität (Discord-UX, ein Login für alles) — und vermeiden gleichzeitig rechtliche Haftung für fremde Self-Host-Inhalte? Drei Wege im Vergleich, für Nicht-Programmierer erklärt.

01 · DAS DILEMMA

Zwei Ziele, die sich beißen

Wenn die Cloud (pulse.unicutmedia.com) der zentrale Login-Anbieter für alle Self-Host-Server ist, hat sie technisch immer Macht über deren User — und juristisch damit Verantwortung. Das ist der Kern des Problems.

Was du willst

Discord-Niederschwelligkeit

  • Ein Login, alle Server in einer App
  • Profil (Name + Avatar) ist überall gleich
  • User wechselt zwischen Servern ohne neues Konto
  • Setup für Self-Hoster bleibt einfach
Was das rechtlich erzeugt

Mitverantwortlich für alles

  • Cloud sieht jede Login-Aktivität (Privacy-Leak)
  • Cloud kann jeden User auf jedem Server sperren → muss reagieren wenn jemand sich beschwert (DSA)
  • Beschwerde-Eingang → 24-72h Frist → Suspension wenn keine Reaktion
  • Cloud ist „passende Intermediary" — kann sich nicht raushalten
02 · WIE ES IM AKTUELLEN PLAN LÄUFT

Klassisches Single-Sign-On

Im Plan, wie er gerade steht: Die Cloud ist Identity-Provider wie Google oder Facebook. Jeder Login geht über sie, jeder Token-Refresh kommt zurück zu ihr. Sie sieht mehr, als sie sehen müsste.

Cloud im Token-Strom — sie sieht jeden Login und jeden Refresh, auch wer wo aktiv ist

Cloud sieht (heute)

  • Bei welcher Instance User Alice ein Token angefordert hat (= welche Server sie nutzt)
  • Wann Alice ihren Token erneuert (alle 5 Min) = „ist gerade aktiv"
  • Welche Server bei Alice in der Sidebar sind (theoretisch herleitbar)
  • Aktivitätsmuster (wann online, wann nicht)

Cloud sieht NICHT

  • Inhalte der Nachrichten
  • Mitglieder-Listen der Self-Host-Guilds
  • Voice/Stream-Inhalte
  • Freunde / DMs auf Self-Hosts

04 · IDEE A IM DETAIL

Identitäts-Zertifikat — der „Personalausweis"-Ansatz

Stell dir vor

Ein Standesamt stellt dir einen Personalausweis aus. Wenn du in eine Bibliothek gehst, zeigst du den Ausweis. Die Bibliothek kann ihn echt-prüfen, indem sie das Wasserzeichen + Hologramm anschaut — sie muss nicht beim Standesamt anrufen.

Das Standesamt erfährt nie, in welche Bibliotheken du gehst. Sie haben dir nur einmal den Ausweis ausgestellt. Was du damit machst, bleibt zwischen dir und der Bibliothek.

Genau so funktioniert das technisch: Cloud ist das Standesamt, dein Browser hält den Ausweis, jeder Self-Host ist eine Bibliothek, die den Ausweis vor Ort verifiziert. Schritt für Schritt:

1
Du registrierst dich ganz normal auf der Cloud
Username, Passwort, MFA — alles wie heute geplant. Pulse-Cloud kennt dich. Das ist der „Personalausweis-Antrag".
2
Dein Browser erzeugt ein eigenes Schlüsselpaar
Wie ein Schlüssel-Bund: einen privaten Schlüssel (bleibt im Browser, niemand sieht ihn) + einen öffentlichen Schlüssel (kann jeder sehen). Mathematik garantiert: nur wer den privaten Schlüssel hat, kann beweisen dass er „du" ist.
3
Cloud signiert ein „Identitäts-Zertifikat"
Cloud nimmt deinen öffentlichen Schlüssel + deinen Username + deinen Avatar + ihre eigene digitale Unterschrift und packt alles in ein Zertifikat. Dieses Zertifikat geht zu dir. Cloud kann es nicht widerrufen, ohne dass sie es selbst auf eine „gesperrt"-Liste setzt.
4
Du fügst einen Self-Host hinzu
Self-Host bekommt dein Zertifikat. Er prüft die Cloud-Signatur (mit dem Cloud-Public-Key, den er ohnehin kennt). Dann schickt er dir eine kleine „Beweis-Aufgabe" („signier mir mal diese Nachricht hier"), die du mit dem privaten Schlüssel löst. Damit weiß er: ja, das bist du.
5
Cloud bleibt komplett aus dem Spiel
Self-Host und Browser reden direkt miteinander. Cloud sieht NICHTS davon — weder dass du eingeloggt bist, noch wann, noch auf welchem Server. Sie wird erst wieder gefragt, wenn das Zertifikat abläuft (z.B. nach einem Jahr) oder wenn dein Account global gesperrt wird (Cloud-CRL-Liste).
6
Pro Self-Host eine eigene „Adresse"
Damit Self-Hosts untereinander nicht herausfinden können „aha, das ist auch der Cloud-User Nr. 42", bekommst du auf jedem Self-Host einen anderen Pseudonym-Identifier. Self-Host A sieht „Alice mit Adresse abc123", Self-Host B sieht „Alice mit Adresse xyz789" — beide wissen nicht, dass das derselbe Cloud-Account ist. Du als User merkst davon nichts, dein Avatar ist überall der gleiche.

Was Cloud jetzt noch sieht (Vergleich)

Cloud sieht NICHT MEHR

  • Auf welchen Self-Hosts du eingeloggt bist
  • Wann du wo aktiv bist (kein Token-Refresh-Stream)
  • Welche Self-Hosts du in der Sidebar hast
  • Aktivitätsmuster über Server hinweg

Cloud sieht weiterhin (unvermeidbar)

  • Wann du dein Zertifikat erneuerst (z.B. einmal pro Jahr)
  • Wann du dein Profil änderst (Avatar, Username)
  • Welche Self-Hosts grundsätzlich registriert sind (Instance-Liste)

Die juristische Wirkung: Cloud rutscht von „Identity-Provider mit aktivem Aktivitäts-Tracking" zu „Zertifizierungs-Stelle, die nur einmal jährlich kontakt hat". Das ist sehr nahe an Mastodon's Rechtsposition, obwohl du UX-mäßig weiter SSO anbietest.

05 · MEHRERE GERÄTE GLEICHZEITIG

Web + Electron + Handy parallel — funktioniert das?

Ja, in beiden Modellen. Aber die Mechanik unterscheidet sich — bei Idee C ist es trivial, bei Idee A brauchen wir ein zusätzliches Konzept, das aber sauber gelöst ist (Signal, WhatsApp, PGP machen das alle so).

Bei Idee C — trivial

Wie Discord oder Slack

  • Jedes Gerät loggt sich einzeln ein (Username + Passwort + MFA)
  • Jedes Gerät hat eigenen Token-Satz
  • Web + Electron parallel = zwei unabhängige Sessions desselben Accounts
  • Cloud sieht alle Sessions, kannst einzeln "Abmelden" drücken
  • Null Mehraufwand — gibt's in jeder OAuth-Library
Bei Idee A — Sub-Keys pro Gerät

Wie Signal-Linked-Devices

  • Pro Gerät ein eigenes Schlüsselpaar (privater Key verlässt Gerät nie)
  • Cloud führt eine Liste deiner Geräte-Public-Keys
  • Alle Geräte gehören zur selben Cloud-Identität (gleiche User-ID, gleicher Pairwise-Sub pro Self-Host)
  • Self-Host sieht "Alice ist mit 3 Sessions online" — analog zu Idee C
  • 1-2 Wochen Mehraufwand, sauber lösbar

Konkreter Flow bei Idee A (Multi-Device)

1
Du registrierst dich auf der Cloud (Web-Browser)
Browser generiert Schlüsselpaar 1. Cloud zertifiziert: "Alice, Gerät 1: Web Firefox Linux". Erstes Gerät, alles wie gehabt.
2
Du öffnest später die Electron-App
Electron fragt: "Bitte einmal auf der Cloud authentifizieren" → Username + Passwort + MFA. Electron generiert Schlüsselpaar 2. Cloud zertifiziert als "Alice, Gerät 2: Electron Desktop". Cloud-DB hat jetzt zwei Public-Keys für Alice.
3
Beide Geräte sind parallel nutzbar
Auf jedem Self-Host gehst du als "dieselbe Alice" online, weil beide Zertifikate denselben Pairwise-Sub enthalten. Self-Host sieht "Alice mit 2 Sessions" — kann nicht unterscheiden, ob das Web oder Electron ist (Privacy-Bonus).
4
Drittes Gerät dazu: Handy unterwegs
Gleiche Prozedur: einmal authentifizieren, neues Keypair, neues Zertifikat. Cloud-DB hat jetzt 3 Geräte. Alle parallel, alle als "Alice" überall.

Edge-Cases — was wenn…

…Browser-Cache geleert

Dieses Gerät kann sich nicht mehr ausweisen → Re-Login auf der Cloud → neues Keypair, neues Zertifikat. Das alte Gerät verfällt automatisch nach Inaktivität (oder wandert in die Sperr-Liste). Aus User-Sicht: wie ein normaler Re-Login.

…Laptop wird geklaut

Auf einem anderen Gerät einloggen → in den Cloud-Settings das geklaute Gerät einzeln sperren → kommt nirgendwo mehr rein. Binnen ~30 Sekunden auf allen Self-Hosts inaktiv (durch die Revocation-List-Pull-Mechanik).

…ALLE Geräte verloren

Du brauchst eine Backup-Methode: Backup-Codes (10 Stück bei MFA-Setup, auf Papier ausgedruckt), oder optionales verschlüsseltes Schlüssel-Backup in der Cloud (mit Master-Passwort, nur du kennst es). Ohne beides: Account weg. Hart, aber sauber — wie bei Banking-Apps.

…parallel im Voice-Channel?

LiveKit erlaubt mehrere Sessions pro User. Du kannst theoretisch auf Web UND Electron gleichzeitig im selben Voice-Channel sein (hörst dich dann selbst). Discord verhindert das auch nicht — UX-Entscheidung, kein Architektur-Problem. Optional: Warn-Dialog beim Join.

06 · IDEE C IM DETAIL

Reddit-Style — Hausordnung + Mietvertrag

Stell dir vor

Reddit erlaubt jedem, einen Subreddit zu erstellen. Aber: jeder Subreddit-Moderator akzeptiert vorher die Reddit-Sitewide-Regeln und ist vertraglich verpflichtet, sie auf seinem Subreddit durchzusetzen. Reddit greift nur ein, wenn ein Moderator versagt.

Reddit-Inhalte sind formal vom Subreddit verantwortet, aber Reddit setzt die übergreifenden Regeln und kann jeden Subreddit sperren — das gibt Reddit eine viel stärkere rechtliche Position als „wir wissen von nichts".

Bei Pulse würde das so aussehen: Cloud setzt globale Content-Policy. Self-Hoster akzeptiert beim Onboarding einen verbindlichen Vertrag. Bei Verstoß: Cloud kann die ganze Instance sperren — der Hoster trägt aber die Haupt-Verantwortung für seine Inhalte.

1
Cloud hat eine globale Content-Policy
Klare Regeln: kein CSAM, keine Volksverhetzung, keine Plagiate kommerzieller Inhalte etc. Wird öffentlich publiziert. Gilt verbindlich für alle Self-Hosts.
2
Self-Hoster registriert seine Instance
Beim Onboarding: Click-Wrap-Vertrag. „Ich, Hoster von chat.firma.de, akzeptiere die Pulse-Content-Policy und bin verantwortlich für die Inhalte auf meinem Server. Ich werde Beschwerden binnen 48-72h bearbeiten."
3
User kann auf der Cloud Beschwerden einreichen
Öffentliches Formular: „Auf chat.firma.de wird gegen die Content-Policy verstoßen, hier die Beweise." Cloud loggt, sendet Notice an Self-Host-Admin mit Frist.
4
Self-Host muss reagieren
Innerhalb der Frist: entweder „erledigt, hier das Audit-Log" oder „wir lehnen Beschwerde aus folgenden Gründen ab". Keine Reaktion → Cloud suspendiert die Instance.
5
Bei schwerwiegenden Verstößen: Sofort-Suspension
CSAM oder offensichtlich strafbare Inhalte → Cloud sperrt die Instance ohne Frist. Self-Hoster kann widersprechen + Wiederherstellung beantragen.

Vergleich zu Reddit

Reddit verdient mit dem Modell ~1 Mrd USD/Jahr und hat dabei eine vergleichsweise stabile rechtliche Position — obwohl auf einigen ihrer Subreddits durchaus problematische Inhalte landen. Der vertragliche Shield + die globalen Sitewide-Rules + die schnelle Reaktion auf Beschwerden sind das Rezept.

08 · ENTSCHEIDUNG

Was wir machen

CHOSEN PATH · 2026-05-25

Idee A + Idee C zusammen, von Anfang an

Beide Wege werden parallel umgesetzt. Wir wollen das einmal richtig bauen, statt später nachzurüsten. Die rechtliche Position (Idee C) UND die technisch garantierte Privacy (Idee A) entstehen damit gleichzeitig.

Was das im Code bedeutet (vereinfacht): Die Cloud wird Zertifizierungs-Stelle statt klassischer Token-Pumpe. Pro Gerät ein eigenes Schlüsselpaar im Browser/Electron. Pairwise-Subjects auf jedem Self-Host. Eine Geräte-Verwaltungs-UI in den Cloud-Settings. Plus AGB + Self-Hoster-Vertrag + Notice-and-Action-Endpoint für die rechtliche Position.

Was du als User merkst: einmal auf Cloud einloggen, dann auf allen Self-Hosts mit demselben Profil unterwegs — wie Discord. Multi-Device (Web + Electron + Handy) funktioniert wie gewohnt. Aber: Cloud weiß nicht, wo du gerade aktiv bist. Und wenn jemand fragt „wer ist hinter Alice auf chat.firma.de?", kann das technisch niemand mehr beantworten — nicht mal die Cloud.

Aufwand: mehr als Idee C allein (1–2 Monate zusätzlich), aber substanziell weniger als der spätere Umbau. Und das Marketing-Argument „echte Privacy, technisch garantiert" ist ein echtes Differenzierungsmerkmal gegen Discord — und für Self-Hoster das beste Vertrauens-Signal überhaupt.

09 · PLAN-STATUS (nach 5 Reviews)

Was seit dem Mockup entschieden wurde

Die Architektur-Entscheidung „Idee A+C zusammen" ist gefallen. Danach lief der Plan durch fünf systematische Review-Durchgänge — ~103 Findings wurden gefunden und eingearbeitet. Hier die wichtigsten Updates die den User direkt betreffen:

Cert-Modell wird zwei Artefakte haben

Statt nur einem Identitäts-Zertifikat: Identity-Cert (stabil, 1 Jahr) + Profile-Statement (24h, enthält Username/Avatar). Avatar-Wechsel wirkt schnell ohne Cert-Neuausstellung.

Username jederzeit änderbar

Mastodon-Style. Alter Username 30 Tage reserviert (Anti-Squatting).

Self-Hosts werden als Single-Container verteilt

Ein docker run-Befehl, alles drin (Postgres, Redis, LiveKit, MediaMTX, Caddy, coturn). Auto-Updates via Watchtower default-an, kein Opt-out.

Update-Sicherheitsnetze

Pre-Migration-Test im CI, Auto-Backup vor jedem Update, Health-Probe + E-Mail-Notify bei Failure, Staged Rollout (Cloud-Production 15-Min-Canary, dann Self-Hosts).

Suspension auf zwei Pfaden

Cloud kann Self-Host suspendieren: Self-Host pollt eigenen Status + Frontend markiert Server als gesperrt. Doppelter Schutz.

Plugin-System integriert

Plugins (hello, tamagotchi, künftige) sind im Container-Image gebaked. Updates kommen automatisch. State pro Instance isoliert.
